# XH-202625 遥感目标检测竞赛 Demo 设计

日期：2026-06-19

## 1. 目标

在正式比赛数据开放前，使用公开遥感数据建立一套可复现的竞赛基线，完整验证以下闭环：

1. 遥感数据转换与三类目标映射；
2. 旋转框目标检测模型训练；
3. 10,000×10,000 像素超大图滑窗推理；
4. 跨切片检测框合并；
5. 比赛规则评测；
6. COCO JSON 结果导出；
7. 可视化 Demo 展示。

首轮目标是在三天内完成可运行闭环，随后用四天进行精度、虚警率、速度和稳定性优化。该 Demo 是竞赛工程基线，不是单纯的展示页面。

## 2. 比赛目标与约束

比赛要求在少量、类别高度不均衡的光学遥感卫星影像中检测以下三类陆上或近岸目标：

- 飞机；
- 舰船；
- 车辆。

初赛刚性指标为：

- 三类合并召回率不低于 85%；
- 三类合并虚警率不高于 20%；
- 单幅 10,000×10,000 像素图像推理时间不超过 20 秒；
- 测试设备为单张 NVIDIA RTX 3090 或同等算力设备。

比赛匹配规则为：

- 预测按置信度从高到低依次匹配；
- 每个预测框最多匹配一个真值框；
- 每个真值框最多被一个预测框匹配；
- 同一真值的重复检测除最高置信度匹配外均计为 FP；
- 车辆匹配阈值为 IoU≥0.35；
- 飞机和舰船匹配阈值为 IoU≥0.50。

指标定义：

```text
Recall = TP / (TP + FN)
FDR    = FP / (FP + TP)
```

计时在图像数据已加载到内存后开始，在生成最终检测结果后结束。单独记录预处理、模型推理、后处理和总耗时，避免对性能瓶颈作错误判断。

## 3. 第一周范围

### 3.1 包含

- DOTA-v1.5 训练集和验证集的数据适配；
- 飞机、舰船、车辆三类归并；
- YOLO26s-OBB 基线训练和推理；
- 普通图与超大图推理；
- 跨切片结果合并；
- OBB、HBB 和 COCO JSON 输出；
- 比赛规则评测器；
- Gradio 展示页面；
- 自动化测试、配置文件、日志和 README。

### 3.2 不包含

- 第一周不修改模型网络结构；
- 第一周不引入 FAIR1M；
- 第一周不承诺达到正式比赛的 85%/20%/20 秒指标；
- 不使用光学-SAR 双模态融合，因为比赛当前只明确提供光学数据；
- 不把前端页面开发放在算法闭环之前；
- 不在缺少正式数据分布信息时过早实现复杂的小样本算法。

## 4. 数据设计

### 4.1 公开数据选择

首选 DOTA-v1.5，原因如下：

- 原始图像尺寸覆盖约 800×800 至 20,000×20,000 像素，适合验证超大图处理；
- 使用四点旋转框标注；
- 覆盖飞机、舰船、小型车辆和大型车辆；
- 包含大量小于或接近 10 像素的极小目标；
- 数据具有尺度、方向、传感器和背景差异；
- 可同时验证旋转框训练和水平框评测。

DOTA 数据仅用于本次学术竞赛研究，并遵守其仅限学术用途的许可要求。

### 4.2 类别映射

| DOTA-v1.5 类别 | 统一类别 | 内部类别 ID |
|---|---|---:|
| plane | aircraft | 0 |
| ship | ship | 1 |
| small vehicle | vehicle | 2 |
| large vehicle | vehicle | 2 |

其他类别不作为正样本，但其图像区域仍保留为复杂背景。数据转换器不得简单删除含其他类别的整幅图像，否则会降低负样本和背景多样性。

### 4.3 内部标注格式

内部统一使用：

```text
image_id
class_id
confidence（真值为空）
x1, y1, x2, y2, x3, y3, x4, y4
difficult
```

四个顶点按顺时针排序。训练时转换为 Ultralytics OBB 格式：

```text
class_id x1 y1 x2 y2 x3 y3 x4 y4
```

坐标归一化至 `[0, 1]`。输出阶段从 OBB 生成外接 HBB：

```text
xmin = min(x1, x2, x3, x4)
ymin = min(y1, y2, y3, y4)
xmax = max(x1, x2, x3, x4)
ymax = max(y1, y2, y3, y4)
```

### 4.4 正式数据接入

正式数据发布后新增独立适配器，负责：

- 读取官方目录和标注格式；
- 映射官方类别 ID；
- 判断官方提供的是 HBB、OBB 或其他多边形；
- 生成统一内部格式；
- 保留官方 train/val 划分或按场景划分，避免同一区域切片泄漏；
- 根据官方提交规范调整最终 JSON 字段。

训练、推理、切片、合并和评测模块不依赖具体数据集目录结构。

## 5. 模型基线

首选 `yolo26s-obb.pt`：

- 官方 OBB 权重在 DOTAv1 上预训练；
- 1024 输入下速度和精度较均衡；
- 4090 的 24GB 显存可以支撑首轮训练和批量推理；
- 支持四点 OBB 输出，适合任意方向遥感目标；
- 后续可以无缝比较 n、m 等规模。

训练策略：

- 输入尺寸从 1024 开始；
- 使用 DOTA 预训练权重微调；
- 首次训练先验证数据和损失是否正常，再增加 epoch；
- 保存最佳权重、最后权重、训练参数、包版本和指标；
- 固定随机种子并记录数据清单；
- 自动选择可用 batch，显存不足时只降低 batch，不静默降低输入尺寸；
- 正式比赛以召回率和 FDR 为主，不以公开数据 mAP 作为唯一决策依据。

Ultralytics 版本必须固定为实际测试通过的版本。模型文件、许可证信息和依赖版本写入 README。

## 7. 模块职责

### 7.1 数据适配器

职责：

- 解析 DOTA 或正式数据；
- 类别归并；
- 标注合法性检查；
- 生成训练配置和图像清单；
- 输出类别数量、目标尺寸和长尾分布统计。

该模块只负责“数据变成统一格式”，不包含模型训练逻辑。

### 7.2 滑窗切片器

默认参数：

- 切片尺寸：1024×1024；
- 重叠比例：20%；
- 边缘使用补边保证固定尺寸；
- 每个切片保存原图 ID、左上角偏移、有效区域和缩放比例。

后续对 1024/1280 输入和 10%/20%/30% 重叠率做速度与召回率对比。

### 7.3 推理器

职责：

- 加载 PyTorch 或 TensorRT 模型；
- 对切片批量 FP16 推理；
- 统一输出四点 OBB、类别、置信度和切片元数据；
- 分阶段计时；
- 支持普通图绕过滑窗流程。

首轮使用 PyTorch 权重保证开发速度，闭环稳定后再评估 TensorRT FP16。

### 7.4 坐标回映与跨切片合并

流程：

1. 将切片 OBB 加上切片偏移，恢复全图坐标；
2. 裁剪越界坐标；
3. 对切片边缘的截断目标降低优先级或丢弃明显残框；
4. 按类别进行旋转 IoU 合并；
5. 输出保留框；
6. 转换为 HBB 供比赛评测。

首轮使用 class-wise rotated NMS。WBF 作为后续可选实验，不与基线同时引入。

### 7.5 比赛评测器

评测器独立于 Ultralytics 自带 mAP 评测，实现比赛原始规则。

输出内容：

- 总体 TP、FP、FN、Recall、FDR；
- 飞机 TP、FP、FN、Recall、FDR；
- 舰船 TP、FP、FN、Recall、FDR；
- 车辆 TP、FP、FN、Recall、FDR；
- 图像级明细；
- 每阶段耗时统计；
- 不同置信度阈值对应的 Recall/FDR 曲线和可行区间。

阈值搜索不能只优化整体结果，还要观察三类各自排名，因为评分方案会分别对三类召回率、虚警率及总时效性排序。

### 7.6 COCO JSON 导出器

每条预测至少包含：

```json
{
  "image_id": 1,
  "category_id": 0,
  "bbox": [x, y, width, height],
  "score": 0.95
}
```

正式数据开放后，以官方 image_id、category_id 和字段规范为准。导出前检查：

- ID 是否存在且唯一映射；
- 坐标是否位于图像范围内；
- width、height 是否为正；
- score 是否在 `[0, 1]`；
- 是否包含 NaN 或 Infinity；
- 是否存在明显重复框。

### 7.7 Gradio Demo

页面功能：

- 上传普通图或超大图；
- 选择模型、置信度阈值、切片尺寸和重叠率；
- 显示切片及推理进度；
- 展示 OBB 或 HBB 检测结果；
- 显示三类目标数量和耗时；
- 上传真值时显示 Recall/FDR；
- 下载可视化图片和 COCO JSON。

页面调用与命令行相同的推理服务，不复制算法逻辑。

## 8. 异常处理

- 图片损坏：记录文件名和错误，跳过该图；
- 空标注：作为合法负样本处理；
- 非法标注：记录越界、面积为零、顶点重复等原因；
- 显存不足：降低 batch 后重试，并在日志中记录；
- 超大图中途失败：保存切片预测缓存，从未完成切片继续；
- 无预测结果：输出合法空 JSON 和零目标统计；
- 无真值结果：不计算 Recall/FDR，只输出检测结果；
- JSON 校验失败：阻止生成最终提交包；
- 运行环境差异：启动时输出 GPU、CUDA、PyTorch、Ultralytics 和驱动版本。

## 9. 测试设计

### 9.1 单元测试

- OBB 转 HBB；
- 切片局部坐标回映到全图；
- 边缘补边和有效区域；
- 车辆 IoU=0.35 的边界匹配；
- 飞机/舰船 IoU=0.50 的边界匹配；
- 多个预测框匹配同一真值时只保留一个 TP；
- 空预测、空真值和二者同时为空；
- 类别错误不能匹配；
- COCO JSON 字段和坐标校验；
- 相邻切片重复检测合并。

### 9.2 集成测试

- 使用 DOTA8 或少量 DOTA 图像完成训练、验证、推理闭环；
- 使用若干 DOTA 原始大图验证滑窗处理；
- 拼接生成 10,000×10,000 模拟图，验证内存、耗时和坐标；
- 从命令行和 Gradio 分别运行同一图像，结果应一致；
- 在全新 4090 实例中依据 README 完整复现。

### 9.3 性能测试

- 首次加载模型的冷启动时间不计入逐图比赛推理；
- 正式计时前预热 GPU；
- 每个配置重复多次，报告中位数和 P95；
- 分别测试 PyTorch FP16 和 TensorRT FP16；
- 不使用会造成不公平缓存的数据读取方式；
- 重点验证 10,000×10,000 图像处理是否接近 20 秒目标。

## 10. 三天冲刺与四天优化

### 第 1 天：跑通模型

- 创建环境并固定依赖；
- 使用 DOTA8/DOTA128 做冒烟训练；
- 下载 DOTA-v1.5；
- 完成三类数据转换；
- 使用预训练权重运行首轮 OBB 推理；
- 检查类别、坐标和可视化。

### 第 2 天：跑通超大图

- 启动完整数据微调；
- 开发滑窗切片和批量推理；
- 完成全图坐标回映；
- 完成跨切片 rotated NMS；
- 生成 OBB/HBB 可视化。

### 第 3 天：完成竞赛闭环

- 完成比赛评测器；
- 完成 COCO JSON 导出和校验；
- 完成 Gradio 页面；
- 完成 README 和一键命令；
- 用模拟 10,000×10,000 图像演示。

### 第 4 天：控制虚警

- 搜索全局和分类别置信度阈值；
- 分析常见 FP；
- 增加 hard-negative 场景；
- 比较 NMS 参数。

### 第 5 天：提升小目标召回

- 比较输入尺寸；
- 比较滑窗重叠率；
- 分析切片边缘漏检；
- 比较 n/s/m 模型和训练时长。

### 第 6 天：速度优化

- 优化 batch；
- 启用 FP16；
- 减少不必要的数据复制；
- 导出 TensorRT；
- 测量各阶段耗时。

### 第 7 天：稳定和汇报

- 新环境复现；
- 异常输入测试；
- 固化最佳配置；
- 准备检测结果、训练曲线、指标表和演示流程。

## 11. 正式数据开放后的迭代顺序

1. 接入正式数据并复现公开数据基线；
2. 统计正式数据的类别数量、尺寸分布、场景分布和难例；
3. 使用分类别阈值与 hard-negative mining 控制虚警；
4. 引入类别均衡采样、稀有类 Copy-Paste 和损失重加权；
5. 评估 P2 小目标检测层或更高分辨率特征；
6. 评估伪标签、半监督学习和教师学生蒸馏；
7. 进行消融实验，确保创新对 Recall、FDR 或速度有可量化贡献；
8. 在 RTX 3090 上完成最终 20 秒约束验证。

所有创新都必须以基线为对照，并分别报告飞机、舰船、车辆和总体指标。

## 12. 验收标准

第一周结束时，项目满足：

- 一条命令启动 Demo；
- 一条命令运行训练；
- 一条命令运行超大图推理和 COCO JSON 导出；
- 一条命令运行比赛规则评测；
- 10,000×10,000 模拟图能完整切片、推理和合并；
- 评测规则通过手工构造测试；
- 普通图和超大图均可视化；
- 配置、权重来源、依赖和复现步骤完整记录；
- 正式数据接入只需实现适配器和类别配置。
